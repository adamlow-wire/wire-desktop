## SEC-009 main-to-preload notification request

`EVENT_TYPE.ACTION.REQUEST_NOTIFICATION_PERMISSION` is a fixed, argument-free **main-to-account-preload** command, not a renderer-to-main grant endpoint. The isolated preload invokes the browser's notification request, ignores malformed/duplicate pending commands, and publishes only `granted`, `denied` or `default` through the existing `WebAppEvents.NOTIFICATION.PERMISSION_STATE` adapter. Errors are contained with a generic diagnostic. Session permission policy still decides whether consent can grant access. Main-owned initiation requires a ready, visible, consent-eligible native account and runs once per document; the localized Notifications menu retries through the bound-window/controller route. Existing account-event authorization gates `loaded` notifications. No renderer-selected grant endpoint is introduced. PR #47 integrates this consent/capability composition after final-head native/platform and product allow/reload-denial qualification; DEC-009 is accepted and display capture remains denied.

CAP-005 September 14 candidate retains the exact-active-prompt channels and payload contracts. Their coordinator actions now capture the native challenge's web contents: submission applies proxy settings there, and cancellation clears its session/reloads that view. The main shell and unrelated sessions are not targets. A real two-account challenge reproduced the old cross-account mutation before the fix; final platform qualification remains pending.

CAP-005 automatic proxy authentication has no renderer IPC entry point. Native challenge host/port must match configured system credentials before automatic use; absent, unreadable or foreign settings require the registered prompt. The real negative target forbids transmitting foreign credentials. This strengthens the existing prompt/session contract without adding a capability.
